Your backlog of small, well-defined engineering work, fixed while you sleep.

menD watches the repositories you register. When an issue carries the menD:fix label, it decides whether the issue has a definition of done a machine can check, writes that contract down, and then uses the Devin API to do the work: one session to scope, one to implement, test and open the pull request. Anything ambiguous is handed straight back to a human, labelled and explained.

How it works

The four decisions menD makes for you

Is this automatable at all?

A scoping session restates the problem, lists acceptance criteria, the commands that prove them, the files in scope and the test that will cover the fix. No verifiable contract, no remediation — the issue is labelled menD:not-a-candidate with the reason.

What does “done” mean?

The accepted contract is hashed and stored, and the remediation session is held to it. Every PR states which criteria were met, which commands were run and which tests were added or changed — or why no test change was warranted.

Who owns this work right now?

Each task is claimed with a lease and a predicted completion time, renewed by heartbeat while a worker is active. If that worker dies, any other stateless worker reclaims the task and resumes from the persisted state. Two workers can never run the same issue.

Do we actually believe the fix?

menD prefers the repository's own required checks as the verdict. Where CI is thin it falls back to a verification contract run and, failing that, records the outcome as UNVERIFIED rather than claiming a green it does not have.
