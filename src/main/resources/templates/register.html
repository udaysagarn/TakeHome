Connect a repository to menD

menD acts on GitHub as its own bot identity, using a GitHub App installation rather than a personal token, so every comment, label and pull request is attributable and every credential it holds is short lived. Six steps, once per repository.

Steps

  1. Install the menD GitHub App on the repository

    Open the app, choose Only select repositories, and pick the repository you want menD to watch. Installing per repository keeps the blast radius explicit.

  2. Grant the permissions menD needs

    Under the app's repository permissions:

    PermissionLevelWhy
    IssuesRead and writeread the issue, apply state labels, post the contract and the outcome
    Pull requestsRead and writefind the PR Devin opened and comment the verification evidence on it
    ContentsRead-onlyread the repository profile sources: build files, test layout, AGENTS.md and friends
    ChecksRead-onlyread the CI verdict that gates success
    MetadataRead-onlymandatory, granted automatically

    If you change permissions after installing, GitHub keeps the old grant until the installation accepts the request — approve it on the installation page, or reinstall.

  3. Create the trigger label

    Add a label named menD:fix to the repository. Applying it to an issue is what puts that issue in menD's queue; menD manages the rest of the menD: labels itself (menD:in-progress, menD:pr-open, menD:not-a-candidate, menD:done, menD:needs-human).

  4. Register it here

    menD validates immediately: that it can see the repository, that the repository is not archived and has issues enabled, that it is inside the app installation, and that the installation actually carries the write permissions above. A failure is kept with the reason so you can fix it and re-validate rather than starting over.

    A full GitHub URL works too — menD normalises it to owner/name.

  5. Let menD learn the repository once

    On the first reconcile after registration, menD runs a single Devin session that reads the repository's build, test, CI and convention surface — AGENTS.md, CLAUDE.md, codex.md, GEMINI.md, .cursor/rules, .agents/skills, CONTRIBUTING.md — and persists it as the repository profile. Every later scoping and remediation session is primed with that profile instead of re-reading the codebase, and pushes that touch those files mark only the affected slices stale.

  6. Optional: merge the verification contract

    If your repository already runs required checks on pull requests, skip this — menD waits on them and treats them as authoritative. If it does not, copy deploy/target-repo/mend-verify.yml into .github/workflows/mend-verify.yml and merge it. menD then asks your CI to run the commands agreed at scoping time, inside your own toolchain, and believes that check run.

    menD never executes your test suite inside its own container. Without either of these, a pull request is reported as unverified rather than remediated — an honest gap, not a green tick.
