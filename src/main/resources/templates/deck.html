What

Every engineering team carries a backlog of work that is too small to schedule and too real to close.

menD is an event-driven control plane that watches your repositories, decides which of that work has a definition of done a machine can check, and uses Devin to do it — with the evidence attached, or with the honest admission that nothing could prove it.

Every number and every link in this deck is read from the instance serving it, so the pitch cannot drift from what the board says.

What

The problem is not that the work is hard. It is that the work never gets picked.

What actually happens today

  • A flaky lockfile pin, a deprecated call, a missing test — each an hour of work.
  • Each still costs a context switch, a review, a CI wait, a merge.
  • So it waits behind the roadmap, and the backlog only grows.
  • When it is finally picked up, the person doing it is your most expensive engineer on their least valuable day.

Why generic automation has not solved it

  • Bots that only open PRs move the work, they do not finish it.
  • Rules-based tooling cannot tell a bounded issue from one that needs a product decision.
  • Nothing in the usual stack can read the issue, write the fix, run the tests and answer the reviewer.

The hard part was never the code. It is the judgement about which issues are safe to automate, and the proof that the fix is real.

What

So menD is built around two refusals.

It refuses ambiguous work

Before any code is written, a scoping session must produce a contract: acceptance criteria, the commands that prove them, the files in scope, and the test that will cover the fix. No contract, no session — the issue is labelled menD:not-a-candidate with the reason, and a human keeps it.

It refuses unproven success

SUCCEEDED requires evidence from something other than the session that wrote the code. Where no such evidence exists, the outcome is UNVERIFIED — a column on the board, counted against the success rate, never quietly rounded up to green.

Those two refusals are what make the rest of it safe to leave running.

How

One issue, end to end.

  1. Ingest

    A human labels an issue menD:fix. A webhook or the 30-second poller creates one durable row, keyed on (repo, issue_number) so a duplicate event can never fork a second task.

  2. Scope

    A Devin session reads the issue against the repository's stored profile and returns structured JSON: is_candidate, acceptance criteria, verification commands, files in scope, and a test plan. menD hashes that contract and stores it.

  3. Remediate

    A second Devin session — clean context, held to the contract it did not write — implements the fix, adds or updates the tests, runs the commands, and opens the pull request.

  4. Verify

    menD waits on the repository's own required checks. If they exist and pass, that is the verdict. If not, it falls through the tiers, and records what it actually got.

  5. Answer the reviewer

    A human requests changes; menD hands the feedback back to the same session, which keeps its full context. Bounded rounds — after that a human is asked for, not guessed at.

  6. Learn

    A retrospective session turns the reviewer's objections into lessons, split into repository-specific and general, and the repository ones are injected into the next session on that repository.

This instance did exactly that on repo#2: the pull request Devin opened landed with independent evidence behind it.

How

The architecture, in one picture.

How

Four decisions your senior engineers will ask about.

The database is the system of record — not GitHub labels

Labels are not transactional, are rate-limited, and hold no history. They are a human-visible projection of state. The truth is a row: state, contract, session ids, attempts, evidence, plus an append-only event per transition.

Every task is leased, with a deadline

A worker claims a task with a conditional update — owner_id, lease_expires_at, eta_at — and renews by heartbeat. Two workers can never hold one issue; a worker that dies has its lease expire and any other stateless worker resumes from the persisted state.

Repositories are indexed once, not re-read per issue

At registration menD validates access and builds a profile — stack, commands, layout, tests, CI, PR conventions, plus AGENTS.md, CLAUDE.md, codex.md and .cursor/rules. Pushes refresh only the slices the changed paths touch.

Verification is tiered, and the tier is recorded

Repo CI → a menD / contract workflow that runs the agreed commands in the repository's own environment → a command-only verifier session → UNVERIFIED. The tier and the raw exit codes are shown on the task page and posted to the PR.

Why Devin

Three things in this system are impossible without an autonomous coding agent.

Judgement before code

The candidacy gate is not a rule set — it is a session reading an issue against a codebase and deciding whether a machine-checkable definition of done exists. That is the step that makes it safe to run unattended, and no amount of pattern matching produces it.

The work itself, across N repositories

menD holds no toolchain. Devin brings its own environment per repository, so adding a Python repo next to a TypeScript one costs a registration, not an integration.

A session that survives the review

When a reviewer objects, menD replies to the original session — the one that still holds why it made each choice. A stateless code generator would have to be re-briefed and would happily re-make the same mistake.

menD's own contribution is the part Devin should not have to own: durability, leases, budgets, verification tiers, and the refusal to claim a green it does not have.

Why Devin

And it compounds, which is the actual business case.

Every review a human writes becomes a lesson. Repository lessons ride into the next session on that repository; general lessons are surfaced for a human to promote into org-wide Devin knowledge. Lessons that stop earning their keep are retired, so the prompt does not grow without bound.

When

What this is not, yet.

  • Single-node by deployment, not by design — the leases are already the hard part; running replicas needs Postgres and nothing else.
  • The contract workflow has to be merged into each target repository before it can be the verification tier, which is deliberate: the harness is auditable in your repo, not hidden in ours.
  • Promotion of a general lesson into org-wide Devin knowledge is a recommendation for a human to accept. Nothing writes to your organisation's knowledge automatically.
  • Cost control is a per-task ACU budget and bounded attempts — real, but blunt.
When

How I would extend this in a real engagement.

Weeks 1–2 · Prove it on one repository

Register the repository, merge the contract workflow, and run in shadow mode: menD scopes and declines, but a human dispatches every remediation. The output is a candidacy precision number your team believes.

Weeks 3–6 · Widen the intake

Beyond labelled issues: failing flaky tests, dependency advisories, deprecation warnings, lint debt with an owner. Each becomes an issue source with its own gate and its own budget.

Quarter 2 · Make it a platform surface

Postgres and replicas, per-team budgets and quotas, SSO on the board, and the leadership report piped into whatever your VPs already read on Monday morning.

Quarter 2 · Lessons become playbooks

Two Devin playbooks per repository — one for remediation, one for verification — proposed by menD as a diff, approved and owned by your engineers, versioned, with the revision recorded on every task so a change that makes reviews worse can be rolled back.

Ongoing · Close the loop on the loop

Track review comments per PR over time as the real quality metric. If lessons are working, that number falls. If it does not fall, the learning store is decoration and should be cut.
